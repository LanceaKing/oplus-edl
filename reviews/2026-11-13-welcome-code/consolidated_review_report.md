## 三项重点的结论

| 重点 | 结论与依据 |
| --- | --- |
| 空白处理是否吞掉原始数据 | 没有发现请求范围内的丢字节。`qdl/src/lib.rs:249` 只在 XML 文档开始前消费空白；`:263–270` 遇到 `</data>` 即返回。原始数据由 `:730–745` 按剩余长度读取并原样输出，读够请求长度后才在 `:749` 进入最终 XML 解析。真实后端和测试通道的 Read／BufRead 共用消费位置 |
| 是否仍严格要求 ACK | 是。命令响应以 `welcome=false` 调用解析器（`:302`），因此空白、日志、welcome 结束标记、部分 XML 后的超时或 EOF 都不能变为 ACK。program 初始／最终响应以及 read 最终响应仍检查完整 ACK；NAK 仍失败。此结论不代表新增了通用 ACK rawmode 状态校验 |
| 离线回归是否充分 | 对本次目标充分。5 个新测试覆盖 configure 实际调用路径、完整合并／分片／逐字节交接、全空白原始数据保真、后续响应保留、超时／EOF／畸形 XML 及大小边界。独立反向移除生产条件修改后，50 个 Firehose 测试中 3 个预期失败，证明能检出原故障。额外探针覆盖了更多原始字节和失败响应组合 |

文档前空白规则确实从 welcome 扩展到了共享 XML 响应读取器，包括 read 的最终响应。这一影响已在实现文档和新增测试中明确体现。没有新增产品工作流、依赖、传输抽象、自动重试或设备副作用；未发现需要通过增加会话状态来限制此修复的已证实问题。

## 曾提出、随后撤回的疑点

覆盖审阅最初提出 P1：请求 8 字节时，输入 `初始 ACK + "1234567\r\n" + 带 XML 声明的最终 ACK`，当前返回成功并输出 `1234567\r`，基线则因 XML 声明前的 LF 报错。协调者独立复现了同一差异，并在进度消息中一度将其称为回归。

进一步核对后，这不足以证明数据损失。同一字节流也表示 **8 个有效数据字节 `1234567\r`，再接 LF 和 XML 响应**。两个版本均原样输出前 8 个字节；新增空白处理发生在第 9 字节。脚本分片不是独立的 raw／XML 类型边界，不能证明发送端只想发送 7 个数据字节。去掉最终 XML 声明后，基线也接受同样的字节划分，其原错误不是可靠的原始数据完整性校验。

覆盖审阅者核对设计与接口后撤回了 P1；协议审阅者和另一个新上下文审阅者也独立核实了这一区别。没有找到要求最终 XML 前一律禁止空白的现有契约，因此也不将它降级包装成另一个已确认缺陷。原发现、复现日志和撤回说明全部保留：
