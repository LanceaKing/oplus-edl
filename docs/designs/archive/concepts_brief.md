# Rust Oplus EDL 命令行工具

* **作者：** LanceaKing
* **日期：** 2026-11-13
* **状态：** 工作假设。已记录用户需求；尚未开始 Goldfish 评审。

## 概述

为采用 Qualcomm 平台的 Oplus 手机开发一款 Rust 命令行工具，支持 Windows、macOS 和 Linux。该工具与处于紧急下载模式（Emergency Download，EDL，通常称为 9008 模式）的手机通信，通过 Sahara 加载 programmer（烧录程序），再通过 Firehose 检查存储、备份分区、恢复备份及刷写固件。RMX3800 是首个兼容性研究目标。

用户期望的用途包括无法启动时的恢复、降级刷机，以及在受支持设备上执行 bootloader 解锁或重新上锁流程。是否由工具调用 fastboot 尚未确定。应先评估现有 Oplus EDL 实现，再决定由工具自动执行哪些模式切换或后续 bootloader 步骤。是否支持某项操作，必须以具体设备及资源的证据为依据。实现了某条命令，并不代表 RMX3800 会接受该命令。

所有资源都必须免费且公开可获取。资源公开可获取，并不代表获准重新分发该文件。当前设计任务不包含设备操作：不得查询或重启已连接的手机，不得向其加载 programmer 或写入数据。

## 分析

尚未解决的主要依赖是：能否通过兼容的 programmer 获得设备访问能力。Rust 传输实现无法补足缺失的设备授权，也无法让设备接受不兼容的签名镜像。当前 RMX3800 原厂 loader 包含会话认证和分区权限检查。公开的 patch5 候选仍保留了已检查到的 RSA 和权限相关路径；其配套分区表指向项目 23867，而 RMX3800 原厂资源指向项目 23631。应将它视为未经验证的研究候选。

完整备份意味着覆盖设备存储布局中识别出的每个分区，包括所有暴露的存储单元，以及存在双槽位时的两个槽位副本。它不意味着可以获取 RPMB 秘密、硬件密钥或不可访问的安全存储，也不意味着可以生成能迁移到其他设备的克隆。如果任何必需分区无法读取，备份结果必须标记为不完整，并为每个缺失范围说明原因。传输读取完成只能证明捕获到了字节，不能证明运行中的 Android 系统具有文件系统一致性；本方案计划在 EDL 模式下通过 Firehose 捕获数据。

降级有两个独立结果：写入所选镜像，以及成功启动这些镜像。工具必须分别记录两者。不得根据写入成功、固件文件名或相同芯片组推断回滚兼容性。未知的回滚要求必须在计划中明确保留。

保存的备份可能包含与设备绑定的身份和校准数据。恢复前必须检查设备身份、存储几何参数、分区布局及备份文件哈希。如果无法确定设备身份，工具就不能声称已通过同一设备匹配检查。在权限允许时，原始数据回读可以验证写入的字节，但不能证明 Android 能够启动。

## 目标与非目标

### 范围内目标

- 面向 Windows、macOS 和 Linux 的原生 Rust 命令行应用。
- 公开解锁、上锁、备份、恢复、刷写五个一键流程；协议阶段留在内部。
- 显式选择目标连接；存在多部手机时，绝不任意选取其中一部。
- 在设备授权允许的前提下，通过 Sahara 加载 programmer，并执行 Firehose 存储操作。
- 无需连接手机，即可在本地检查 loader、固件包、摘要表和备份清单。
- 支持通过 Firehose 备份全部分区或所选分区，限制内存用量，并记录分块哈希、进度和中断情况。
- 通过可供审阅的计划执行恢复和救砖刷写；计划绑定确切的输入哈希和目标观测数据。
- 支持降级规划和刷写，分别提供写入权限与启动兼容性的证据。
- 记录资源来源：来源 URL、获取日期、哈希、声称适用的目标、实际观测到的目标数据及验证状态。
- 提供机器可读结果和便于人理解的错误信息。
- 依据证据决定是否集成可选的 fastboot 功能，并区分进入 EDL、Firehose 存储操作、模式切换和机型专用的 bootloader 步骤。

### 范围外非目标

- 在流程评估完成前，就认定必须集成或禁止集成 fastboot。
- 使用付费 loader、私有服务凭据或付费授权服务。
- 宣称支持通用的 Oplus 解锁、重新上锁、降级或认证绕过。
- 仅凭文件名或芯片组，就将 patch5 视为已获认可的 RMX3800 支持方案。
- 在当前设计阶段操作手机。
- 承诺仅凭分区镜像就能完整恢复与硬件绑定或不可访问的安全状态。

## 拟议用户流程

公开接口只提供五个主要流程：`unlock`（解锁）、`lock`（上锁）、`backup`（备份）、`restore`（恢复）和 `flash`（刷写）。下文的实现检查支持按任务提供命令并自动串联内部阶段，不要求每个协议阶段都执行一条命令。这些名称描述拟议接口，不代表已经实现对应能力。可执行文件名仍待确定。完成受支持的流程时，用户不应需要串联协议或会话命令。

| 命令 | 用户获得的结果 | 流程内部完成的工作 |
| --- | --- | --- |
| `unlock` | 解锁受支持设备的 bootloader | 检查机型专用方法和前置条件，说明数据影响，执行受支持的准备与模式切换，完成解锁并验证最终状态 |
| `lock` | 为受支持设备的 bootloader 重新上锁 | 独立检查上锁方法及所需固件状态，说明数据影响，执行受支持的模式切换和上锁，并验证最终状态 |
| `backup` | 默认保存所有必需分区，也可明确选择部分分区 | 选择目标、建立所需会话、识别布局、捕获数据、验证本地哈希，并报告覆盖范围和缺失范围 |
| `restore` | 将已保存的备份恢复到匹配的设备 | 验证备份和目标，生成并展示写入摘要，执行已批准的写入，并报告验证结果 |
| `flash` | 安装固件包，涵盖救砖或降级用途 | 验证固件包和目标，生成并展示写入摘要，执行已批准的写入，并区分写入验证与启动兼容性 |

“一键”指由一条命令协调完成受支持的流程。用户不需要分别运行检查、加载 programmer、列出分区、生成计划、执行计划或验证命令。必要输入和目标选择都在该流程内完成。展示与用户有关的进度和结果，不要求用户管理协议阶段。若必须在设备上确认或进行物理操作，则在同一流程内暂停并给出指引。

本地检查、离线预览、保存计划和验证能力通过这五个命令的选项提供，不再增加顶层命令组。具体选项语法尚未确定。纯本地预览不得连接手机或上传 programmer。仅依据已保存观测数据生成的计划仍是暂定计划；执行前必须重新验证输入和目标观测数据。设备流程必须在执行前说明 programmer 上传及预期状态变化。

解锁和上锁是公开流程名称，不是通用支持承诺。如果所选设备没有经过验证的方法，应在修改设备前明确报告不支持。只完成准备步骤，不能报告解锁完成。上锁需要独立的证据和检查，不能假定为解锁的逆操作。是否调用 fastboot 仍是内部实现决策，由受支持的设备流程决定。

## 拟议内部边界

将命令解析和输出与协议状态分离。设置传输层边界，并提供用于离线开发的回放实现。分别实现 Sahara 协商、Firehose XML／原始数据交互、存储布局解析和作业执行，使已记录的失败能够在无手机条件下复现。

显式建模会话状态转换：未连接、已选择、Sahara、programmer 传输、Firehose 协商、需要授权或已获授权、存储就绪、正在传输、失败。重新连接不代表先前的授权或存储几何参数仍然有效。

将设备专用规则保存在带版本和证据引用的配置档案中。不得让配置档案悄然替代签名检查，也不得将未知能力改为已支持。在第二种具体设备流程提出实际需求之前，不引入插件框架。

备份需要带版本的清单，包含设备观测数据、loader 哈希、存储单元及几何参数、主分区表和备份分区表数据、分区范围、分块哈希，以及各范围的处理结果。先将分块写入临时文件，待数据持久化后再提交对应记录；恢复执行前，验证已提交的数据。本地日志无法让设备侧写入成为原子操作。

写入计划需要包含源文件哈希、目标范围、操作顺序、前置条件、排除的分区，以及所选验证方式。遇到非预期的存储响应时停止。超时后不得自动重试写入：应先确定其结果是已知、未知，还是已通过回读验证。

## 已权衡的替代方案

- **将每个协议阶段公开为命令组：** 按用户要求，改为五个主要流程。单独暴露阶段有利于手动调试，但会要求用户自行拼接常规操作。内部实现和作业记录仍保留阶段边界，预览与验证通过流程选项提供。

- **调用 fastboot：** 根据用户更新后的要求，重新纳入评估。它可能用于受支持的模式切换或后续 bootloader 步骤，但已检查的 EDL 存储路径不依赖它。决定自动执行还是手动交接前，应评估可执行文件打包、设备重新枚举后的目标选择、失败报告，以及机型支持情况。
- **使用付费授权服务：** 不符合资源免费且公开可获取的约束，因此排除。
- **将 patch5 作为 RMX3800 默认方案随工具提供：** 当前证据不支持。其配套配置不同，而且尚未测试 RMX3800 是否接受它。
- **从零实现所有协议：** 未选定此方案。选择依赖前，应根据许可证、协议覆盖范围、维护情况和支持的宿主系统评估复用方案。
- **封装现有外部 EDL 工具：** 仍是待评估的替代方案。它可能减少初期协议开发工作，但会引入运行时打包和错误报告方面的依赖。原生 Rust 是既定实现方向；尚未选定依赖。
- **从庞大的机型数据库起步：** 本提案暂缓此方案。小型且有证据支撑的配置档案，比隐含大量兼容性承诺的机型列表更容易验证。

## 关键决策与后续阶段

已确认的需求包括：跨平台 Rust、免费公开资源、Firehose 备份与恢复、救砖和降级流程，以及当前工作期间不操作手机。公开接口限定为解锁、上锁、备份、恢复、刷写五个主要流程。是否调用 fastboot 改为待定的内部设计决策，取代此前的禁止要求。

拟议阶段为：（1）离线资源检查、清单与计划格式，以及已录制的协议测试样本；（2）Sahara／Firehose 传输，并明确报告授权失败；（3）在另行获准使用的测试设备上进行只读捕获；（4）在可恢复的测试目标上验证恢复和刷写；（5）仅在机制和自动化边界确定后，加入机型专用的 bootloader 准备功能及可能的 fastboot 集成。这些阶段不会缩减用户要求的最终范围。

验收应区分解析器／协议测试、各宿主系统编译成功、各宿主系统的实际 USB 测试，以及具体设备／固件的操作结果。回放测试无法证明设备会接受某个 loader。读取被拒绝时，必须生成不完整备份结果；写入中断时，在验证之前必须如实保留结果未知的状态。

用户已确定首个版本的边界：参照现有 GitHub 实现，提供通用 Sahara／Firehose 支持，以及备份、恢复和刷写功能。RMX3800 是否接受 loader，不是该通用版本发布的前提。这也不代表已支持 RMX3800。五流程接口本身不改变此前的版本验收边界：解锁和上锁必须有经过验证的机型专用方法，才能报告支持。下一道关口是取得许可，对这份更新后的假设开展 Goldfish 评审。

### 拟议实现选择

在编写第二套完整协议栈之前，先通过一个小型内部适配层评估 qdlrs。将备份清单、计划验证、作业记录和 CLI 输出保留在产品层。必要时，优先对固定提交的源码依赖做小范围修复。当前设计任务不包含发起上游贡献。

有具体理由说明不能原样采用上游行为。在固定提交的 qdlrs `firehose_program_storage` 中，代码对 `Read::read` 的结果调用了 unwrap，并忽略返回的字节数，随后发送预先初始化为零的缓冲区。因此，在采用评估中，需要显式处理输入短读，并添加回归测试样本。`QdlDevice::drop` 可能在失败后尝试执行 EDL 重置；产品必须明确规定重置策略。这些都是静态观察结果，并非已复现的设备故障。此外，存储例程混入了控制台进度输出，需要建立输出边界，以支持机器可读结果。

| 宿主系统支持 | 在 Windows、Linux、macOS 上构建／测试，并分别记录各系统的实际 USB／串口验证 | qdlrs 后端是候选；平台 CI 不等于硬件验证 |

对齐意味着协议线上行为兼容，且所请求的存储操作结果等价。它不要求照搬短命令名、支持上游每项功能，或沿用上游的失败报告方式。不支持的 XML 标签或表达式必须在构建计划时、任何设备写入之前报错。使用受限语法解析支持的表达式，绝不能将它们作为宿主机代码执行。在计划中保留稀疏镜像的 DONT_CARE 语义，不得悄然将跳过的块视为零。

所有备份文件都必须以“存储单元 + 分区身份”标识，不能只使用分区名称。GPT 无法读取时，只有在容量和扇区几何参数已知的情况下，才可提供整单元原始备份；否则应报告布局尚未确定。完整备份成功必须以明确的覆盖集合为依据，且所有必需范围均无失败。哈希验证只检查文件完整性，不代表 Android 用户数据可以解密或迁移到其他设备。

首个版本的刷写功能不包含 UFS 配置（provisioning）、RPMB 操作、任意内存读取／写入（peek／poke）、Diag、崩溃 RAM 转储或自动执行机型专用认证绕过。这些上游功能不属于用户选定的通用存储里程碑。Bootloader 准备工作仍留待后续机型专用层实现。降级镜像通过通用刷写路径处理，而实际启动兼容性仍需单独提供证据。

### 评审假设

开发跨平台 Rust EDL CLI，实现通用 Sahara／Firehose 备份、恢复和固件刷写功能；评估 qdlrs 作为协议基础，并以 EDL／qdl 作为行为参考。加入明确的多单元覆盖、绑定资源的写入计划，以及如实记录中断结果的机制。不得让首个版本依赖已经验证可用的 RMX3800 loader，也不得在缺乏设备专用证据时宣称支持 RMX3800。

尚未开始 Goldfish 评审。评审者应重点检验：采用现有库与新建协议栈的取舍、精确的 XML／稀疏镜像兼容性、备份完整性、写入中断处理、宿主机驱动假设，以及通用功能与机型支持之间的区别。

### 工作假设与反对理由

首个版本的存储路径仍采用 Sahara／Firehose。将 fastboot 作为可选流程组件评估，分别决定：是否从受支持的起始模式进入 EDL、如何离开 EDL，以及如何完成机型专用的 bootloader 操作。对于已处于 EDL 的设备，开始备份或刷写不应依赖可用的 fastboot 模式。

支持可选集成的最强理由是：经过验证的跨模式流程可以减少手动交接错误。最强反对理由是：模式变化会引入新的设备选择、驱动、打包和失败状态；在这些路径得到验证前，手动交接可能更简单。这两种理由都不能替所有机型作出决定。

按钮标为 FastbootD，不代表使用了 fastboot 传输；成功进入 FastbootD，也不代表支持 bootloader 解锁或重新上锁。Toolkit 示例还会写入存储，应将其建模为需要审阅的写入操作，而不是无副作用的重启。检查到的前端将扇区大小硬编码为 4096 字节，后端则在尝试重置前丢弃了写入命令的结果。因此，应研究其行为，而不能原样照搬实现。本工具的计划必须使用实际观测的几何参数、保留预期修改范围之外的数据，并在无法确定写入结果时停止。

采用任何 fastboot 自动化之前，应记录起始模式、确切支持的操作、预期目标模式、重新连接前后的设备身份、数据影响，以及目标机型证据。明确标出不支持的模式切换。公开的解锁和上锁流程必须明确报告不受支持的目标；这次研究不能证明通用支持，也不能证明支持 RMX3800。

实现检查支持将一键流程作为默认交互方式。在每个流程内自动完成受支持的阶段，并就地引导无法避免的用户操作。具体机型的模式切换和 fastboot 集成仍待确定。Goldfish 评审仍需等待头脑风暴流程要求的准备就绪确认。


## 根据现有实现确定流程设计

决策：采用五个任务级主命令，自动串联内部阶段，不要求用户为每个 Sahara／Firehose 阶段运行独立命令。在对应命令内提供可选的预览、验证和受支持的继续执行能力。具体选项名称留待设计。这是根据源码行为作出的产品决策，不代表所有参考工具都采用相同接口。

以下静态检查使用前文列出的固定提交，未运行任何工具操作手机。

| 实现 | 观察到的交互与控制流程 | 对本工具的启示 |
| --- | --- | --- |
| OplusEdlTool | README 将进入 Firehose 和选择固件包列为独立步骤。但 `StartFlash_Click` 会检查 Firehose 配置，必要时上传 programmer、摘要和签名，再配置并继续刷写。其所选分区备份路径则依赖已选中的分区行，尝试配置时没有同样的上传流程。 | 主刷写操作已串联多个阶段，不能只凭 README 或按钮名称认定所有操作都同样自动化。 |

强制分步命令最有力的理由，是便于诊断和处理部分失败。通过可见的阶段结果、保存的作业记录、离线预览及按阶段继续执行，保留这些控制能力；不必将每个内部边界都变成用户必须执行的命令。失败时应指出失败阶段和已知设备状态，重新验证后才可继续。继续执行绝不能简单重放写入。

备份、恢复和刷写的默认命令应协调完成从准备到验证的流程。写入流程在执行前展示具体变更摘要；用户可以仅预览而不执行。纯本地预览保持离线。任何实时检查或 programmer 上传都必须明确标为设备访问。如果用户选择拆分执行，保存的计划必须绑定输入，并在执行时重新验证目标，不能假定前一个进程的会话仍然有效。

解锁和上锁沿用任务级接口，但这些存储流程的检查不能证明存在完整的解锁／上锁实现。只有在机型专用方法、所需模式切换和最终状态检查都得到验证后，才能启用对应能力。无法避免的物理操作作为流程内的引导暂停；不支持的方法应报告不支持，不能仅完成准备就宣告成功。
