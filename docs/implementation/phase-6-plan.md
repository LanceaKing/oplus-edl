### XML 包的实际适配缺口

三个包的常规 `rawprogram0..5.xml` 均引用以下文件，但 ZIP 中央目录未提供对应的 `IMAGES/<filename>` 条目：

| XML | 引用文件 | 目标标签 |
| --- | --- | --- |
| rawprogram0.xml | super.img | super |
| rawprogram3.xml | oplus | ocdt |
| rawprogram4.xml | sec.dat | secdata |
| rawprogram5.xml | dynamic_nvbk.bin | oplusdycnvbk |
| rawprogram5.xml | static_nvbk.bin | oplusstanvbk_a |

这是按 XML 所在目录解析路径的静态缺项，不代表包内没有对应素材。后续离线分析发现：权限表把 ocdt、secdata、oplusdycnvbk、oplusstanvbk_a 分别关联到包内实际存在的 `oplus23631.bin`、`sec_smt.dat`、`dynamic_nvbk.23631.bin`、`static_nvbk.23631.bin`，但文件均远短于 XML 写入范围，不能只改名或补零。super 则有定义和分区素材。详见[离线适配分析](phase-6-resources/offline-analysis.md)。当前产品没有服务包组装或厂商别名／容器转换；直接选择全部常规 XML 仍不满足输入条件，不能静默跳过缺项。

其他已查到的约束：

- 常规 XML 使用 4096 字节扇区并涉及物理单元 0–5；这说明包的布局要求，不是本机存储实测。后续必须对照设备实际 GPT／LUN／容量。
- `Projectconfig.xml` 标明项目 23631，同时含 `emmcsize="128G"`。此字段与官方列出的 UFS 容量不能简单对应；其厂商语义未核实，不据它推定设备为 eMMC 或 128 GB。
- patch 同时包含 DISK 和本地 `gpt_main*.bin`／`gpt_backup*.bin` 条目。现有产品跳过本地 patch，不证明整包兼容；需要查明是否依赖本地变换。含 DISK patch 时，`required` 按设计在修改前拒绝，best-effort 不能声称补丁内容回读匹配。
- 包内另有 WIPE_PARTITIONS、BLANK_GPT 和 wipe_rawprogram 变体。它们不是默认验收输入，不用通配符把所有 XML 一并执行。
- 16 版本额外含 GKI_IMAGES 和多个 NV 变体。不能混用目录、摘要和镜像。存储固件更新配置也不属于当前产品支持范围。

## 所需资源

### digest／sig 来源与握手补充（2026-11-15）

详见[认证输入追踪](phase-6-resources/authentication-inputs.md)及[结构化证据](phase-6-resources/authentication-inputs.json)。结论：**完整认证输入尚未备齐，不能把包内 DigestsToSign 与任意 `.sig` 直接配成已可用组合。**

- 两个参考工具均从用户所选本地路径取得 digest／sig，未提供本目标的生成器或自动来源匹配。Toolkit 的默认 res/digest、res/sig 在固定提交及本轮检查的 V0.9.7 Windows portable 中均不存在；已查 OplusEdlTool 发布 ZIP 也未附带目标认证材料。
- 六份 DigestsToSign 实际有四种不同内容，属于结构与加载器相符的 SVIP 表候选。两个 `.sig` 是 102／103 字节的 DER 双整数结构，sign_info 只是构建状态文本；它们不能直接替代 verify 路径中的 256 字节签名材料及 4096 字节接收阶段。
- 加载器的 getsigndata 路径建立 verify 检查的前置状态；verify 另有会话数据签名验证。参考工具的自动握手未显式包含 getsigndata，不能直接作为本包原始加载器的完整操作模板。尚未明确实际设备模式、签名输入合法来源、有效期及全套 ACK／raw 边界；未证明一定需要在线账号或可用固定离线 sig。
- 参考工具还有成功状态传播局限：OplusEdlTool 的摘要发送包装器直接返回 true，Toolkit 外层忽略外部握手 Result 后设置已加载。验收不得用这些 UI 状态替代每阶段协议证据。
- 步骤 0 追加检查：固定 programmer 与 NV／GKI 对应表；明确 digest、Sig 各自的格式、来源及会话绑定；明确 getsigndata／verify／表初始化／sha256init 的顺序和停止条件。未补齐时认证准备项记为未通过，不进入“完整 RMX3800 读写流程已就绪”的结论。

### getsigndata 输出、消息布局与公钥追踪

本轮仅检查已有本地材料，详见[会话协议分析](phase-6-resources/session-protocol.md)、[常量与公钥证据](phase-6-resources/session-protocol-evidence.json)及[指令摘录](phase-6-resources/session-protocol-disassembly.txt)。

- `getsigndata` 通过受等级／输出开关控制的 XML 日志输出 Version、平台、Mode、Rand、项目、摘要、ID、NV 和安全状态；它不直接输出完整的待验二进制消息。部分辅助读取失败会采用占位摘要或空 NV，前序 ACK 不足以证明材料有效。
- `verify` 消息为清零后填充的 208 字节；包含 ASCII ID、16 字符十六进制 Rand、两个 64 字符摘要及固定字段。NV 和 SecureBoot 日志不直接进入该消息。完整偏移表见分析，不对整段日志求摘要来替代。
- `W/R` 来自 EnableFlash；另一字段首次为 `Y`、失败后改为 `N`，成功分别设置 AUTH_INTRANET／AUTH_INTERNET 状态。两次共用同一固定 RSA-2048 公钥（指数 65537），验证为 SHA-256／PKCS#1 v1.5；这些状态名不证明已有网络签名服务。
- 参考工具的通用 XML 入口可以表达手工命令，但已查调用链没有收集挑战、匹配会话并取得签名的实现。服务包中的表和短 DER 清单签名仍不能补齐这条来源链。
- 步骤 0 仍未通过：还缺同会话合法签名样本或有依据的签发协议、表摘要有效范围、读取摘要有效性、日志／ACK／raw 边界及 4096 字节响应的完整格式。后续步骤 2 须分开记录前序状态、验签结果和权限就绪；不得仅凭日志、configure ACK 或工具返回 OK 通过。此次不实施认证接入。

### MSMDownloadTool 研究对照与迁移边界

已对照 `docs/research/msmdownloadtool*`，详见[迁移评估](phase-6-resources/msm-comparison.md)和[核验记录](phase-6-resources/msm-comparison.json)。结论：研究方法和通用协议验收案例可迁入；旧 OnePlus AES token、许可证及 MES 流程不能直接填补当前 RSA 会话签名。

- MSM 5.1.75／5.1.77 的三类设备 token 使用 AES-256-CBC 和 XML token/pk 属性，与当前 getsigndata／verify、208 字节 OSIG 消息、4096 字节接收路径不同。两个旧 RSA 公钥也与当前 verify 公钥模数不同。
- 已重新核对旧 token 证据清单的 165 个文件，全部匹配。已有 39 对客户端执行结果不等于当前设备接受；本轮没有重新执行目标程序。

## 执行顺序与验收标准

以下全部是后续计划，当前均未执行。设计要求实机测试另行授权。届时以具体设备、加载器和操作范围为准；一次已授权范围内的正常步骤不重复索要批准。读取也涉及加载器上传和设备会话，不属于本轮许可。

| 步骤 | 操作范围 | 验收标准与继续条件 |
| --- | --- | --- |
| 0. 固定组合和输入 | 在主机上整理资源、确认授权范围 | 记录设备、加载器、固件、主机、后端、产品提交及二进制标识；确认测试分区及恢复途径。未确定写入范围时不进入写入步骤。真实固件输入检查齐全后才进入整包测试 |
| 1. 枚举与精确选择 | 后续授权后枚举候选，不上传加载器 | 未指定设备时列出稳定标识并返回 `input_error`／2；不自动选第一台。显式目标必须精确唯一。多设备场景没有第二台时标记未测，不伪造实机覆盖 |
| 2. Sahara 与 Firehose | 用所选设备和加载器启动一次小分区备份流程，观察连接阶段 | Sahara 正常完成，Firehose welcome／configure 得到有效响应，后端和目标一致；不能把日志当 ACK。拒绝、超时等按原始阶段记录，不继续写入，不因对象释放而 reset。产品没有独立 connect 工作流，不虚构命令 |
| 3. 存储与 GPT | 先显式选定一个 LUN，读取布局 | GPT 有效，分区范围明确；记录扇区大小是默认、手工指定还是设备报告。设备报告冲突则停止。主 GPT 无效时报错，不自动修复。全 LUN 扫描需实际识别单元数量；无法识别时记录限制，不通过读失败猜数量 |
| 4. 小分区备份与回读基线 | 备份一个已选分区，再读到另一个新目录 | 每次字节数均等于目标长度，完整数据加最终 ACK 后才发布 `lun<N>/<name>.bin`；GPT 捕获单独保存。静态区域两次内容应一致；变化无法解释时不选作写入基线。已有文件不静默覆盖，失败保留 `.partial` |
| 5. 所选范围备份 | 扩展到指定多个分区／LUN；具备条件再覆盖全部已列出的分区 | 文件和结果逐项对应 LUN、分区与范围；失败不能汇总成完整成功。省略过滤器只证明已发现 GPT 分区的覆盖，不声明包含 RPMB、未列出区域或全设备所有数据。保存原始备份供后续恢复 |
| 6. 普通镜像恢复 | 首次写入仅限已明确选择的测试分区，先用其原始镜像；默认 best-effort | 摘要列出目标和范围；修改前一次确认。每项取得写 ACK，随后回读全部已知写入范围并匹配，结果 `acknowledged`／`matched`、退出 0。独立备份比较内容。恢复逐项验证后才进入下一项；相同内容回写只证明该回写路径，不足以证明数据确实发生改变 |
| 7. 范围与目录恢复 | 有专用可恢复区域时，使用可区分的受控内容、短镜像和选定目录 | 首次写入前全部映射唯一；无效映射不得产生修改。短镜像仅覆盖源长度加末扇区补零，补齐后不越界；独立读取确认未覆盖尾部不变。目录不要求包含未选分区；排除 `.partial` 与 GPT 捕获，不能宣称完整分区恢复 |
| 8. 受控 XML／稀疏刷写 | 先在同一测试区域测试 XML；再视资源测试真实固件包 | 按 program 文件及节点顺序执行，再 DISK patch，再回读。RAW／FILL 内容匹配；DONT_CARE 保持原内容，且不抹除前序写入的验证要求；重叠区间以最后写入为准。用非零且可区分的基线验证跳过行为。受控 XML 通过不能替代真实固件包验收 |
| 9. DISK patch 和固件包 | 仅在适配关系、范围和恢复方法已确定时执行 | 完整记录实际 XML、镜像、跳过项及 ACK。本地 patch 列出并跳过，原始文件不变；已知依赖本地变换的包在修改前报不支持。DISK patch 预期值未知，不与补丁前内容比较；按下表报告未完成验证，不能以退出 0 作为所有 patch 场景的要求 |
| 10. 显式最终动作 | 单独纳入授权范围后，测试 set-bootable／reboot | 默认两者均不发送。显式请求且前序策略允许时各一次，顺序为验证、启动单元设置、重启；失败时后续项未尝试。ACK 只证明该协议动作确认；设备启动情况另行记录，不推导降级或跨版本可启动性 |
| 11. 恢复测试区域与结案 | 写过受控内容后，用原始备份恢复并独立读取核对 | 原始范围恢复并回读一致，记录最终设备状态。遇到未知修改或会话失步，立即停止当前流程，先人工确认设备状态，再决定恢复；不自动重连、重试或重放全部固件 |

若没有适合写入的测试区域，仍可形成“连接／读取通过，恢复／刷写未测”的部分记录；不得宣布第六阶段实机验收完整通过。不能为了补齐用例而默认改写 boot、GPT、校准或设备身份分区。

## 验证模式及异常判定

在可恢复测试区域核验正常路径。NAK、丢 ACK、失步和不一致等异常以现有离线故障注入证据为基础；不要求在实机写入中拔线或故意破坏数据。自然发生时按此表判定；未发生则注明“实机未覆盖，离线已测”。仅凭进程退出码不能证明没有后续设备命令；需结合可取得的协议记录，否则该断言保留为离线证据。

| 场景 | 应有结果 | 后续行为 |
| --- | --- | --- |
| best-effort／required，已知范围全部匹配 | 写入 `acknowledged`，验证 `matched`，无其他错误时退出 0 | 可继续 |
| best-effort，原始数据前完整读 NAK，仍处于命令边界 | 写入仍已确认，验证 `incomplete`，汇总 `verification_incomplete`／5 | 可继续，但不能报告验证成功 |
| required，运行时拒读或读取失败 | 保留写 ACK，验证未完成／5（无更高优先级错误时） | 停止剩余写入及最终动作；required 不保证写前发现拒读 |
| best-effort／required，验证超时、截断、失步 | 保留已取得的写 ACK，验证未完成 | 停止会话，不重连或自动重试 |
| 回读不一致 | `mismatch`，`execution_failed`／4 | 停止后续修改和最终动作 |
| 修改明确 NAK | `write: failed`，`execution_failed`／4 | 停止 |
| 修改可能已发出但缺少最终 ACK | `write: unknown`，`unknown_write`／6 | 不启动该项验证，后续项未尝试，不自动 reset |
| required，DISK patch 或其他未知预期内容 | 修改前 `unsupported`／3 | 所有修改次数为零 |
| best-effort，DISK patch 已确认 | 可定位区间未验证；位置未知时屏蔽该 LUN 的相关写入验证；最终验证未完成／5 | 会话正常时按策略继续；不声称补丁内容已验证 |
| none | 无验证读取，`not_requested`；操作已确认且无其他错误时可退出 0 | 成功不等于内容匹配；GPT 等定位读取不算验证读取 |
| unlock／lock | 无已验证机型方法时 `unsupported`／3 | 设备访问前返回，不开展解锁／上锁实机实验 |

每个案例同时检查文本结果或 JSON：JSON stdout 必须恰好一个最终对象，进度和提示在 stderr；字节数为十进制字符串，未知值为 null。保存命令参数、退出码和逐项状态；汇总按设计优先级保留未知修改、执行失败等事实，不用“部分成功”遮盖错误。

## 覆盖矩阵与交付记录

先完成一个可用的“设备 × 加载器 × 固件／镜像 × 主机 × 后端”组合。macOS USB、macOS serial、Windows USB、Windows serial、Linux USB、Linux serial 分别记为未测、通过、失败或条件不足；实测哪个组合就只声明哪个组合。不同介质、扇区大小和多 LUN 也分别记录，不要求为了首个组合新增硬件，不把未覆盖项写成通过。

后续在 `docs/implementation/phase-6.md` 记录结论，并链接实际日志。备份镜像及大体积临时输出放在本地验收目录，不提交固件、加载器或含设备数据的镜像。每个案例至少保存：

- 组合标识、日期、产品提交、qdlrs revision、主机／后端及输入文件标识。
- 实际步骤、LUN／分区／字节范围、验证模式和显式最终动作。
- stdout、stderr、退出码、协议证据及独立读取比较结果；缺失证据明确标注。
- 已完成、失败、跳过、未尝试的项，以及最终设备状态和恢复结果。

完成条件：至少一个明确组合的连接、读取、恢复、XML 刷写和已知内容回读取得实机证据；未满足的环节保留为未完成。仅受控 XML 通过时只能声明受控刷写路径通过，真实固件包兼容性仍未验收。DISK patch、最终动作、多设备及其他平台／后端等扩展项按实际覆盖报告，不隐含通用支持。RMX3800 并非通用版本发布前提，刷写或回读通过也不证明系统可启动。
