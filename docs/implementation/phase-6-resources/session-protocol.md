# 16.0.5.740 会话签名协议静态追踪

版本边界补充：[14.1.0.190 原包核查](../../research/rmx3800-session-authorization.md)确认较旧原包没有本文描述的显式 getsigndata 准备标志检查，但仍有 RSA 验签。本文的标志地址和前序要求只适用于下述 16.0 样本；固定 digest/sign 文件路径不能仅因此被排除。

本轮结论：已恢复 `getsigndata` 的主要输出、`verify` 的 208 字节消息布局，以及该分支使用的固定 RSA 公钥。**仍未找到从会话数据取得有效签名的来源链，不能据此宣布认证输入齐全。** 本轮完全使用已有本地材料，没有网络请求，没有运行厂商工具、仿真加载器或操作设备，没有修改产品／依赖代码。

对象仍为 `IMAGES/prog_firehose_ddr.elf`，SHA-256 `daaddec2d87fa2f30a527f0e3d656044ef9e2fdece8163afde856cb9505e34ea`，嵌套 AArch64 ELF 文件偏移 `0x110b50`。下文地址为该模块声明的虚拟地址。证据见[常量、公钥与源文件哈希](session-protocol-evidence.json)及[关键指令](session-protocol-disassembly.txt)。本报告细化[前次认证分析](authentication-inputs.md)，不将静态控制流写成实机观察。

## getsigndata 输出及来源

处理器 `0x149a19b8` 先取得芯片序列字段，再准备 Rand、DigestRead、NV，调用 `0x149a1150` 输出日志，最后设置前序成功状态并调用响应函数。日志格式常量为：

```text
Version:%s; Platform1:%s; Platform2:%s; Mode:%s; Rand:%s; ProjectWrite:%s; ProjectRead:%s; DigestWrite:%s; DigestRead:%s;
ID:%s;
NV:%s;
SecureBoot:enable; 或 SecureBoot:disable;
```

这是格式说明，不是本轮获取的设备输出。`0x149a5c34` 先检查日志等级，再在输出开关允许时经 `0x149a7e00` 包装成 XML `<log value="..." />`，随后发送；它不是一次直接返回 208 字节二进制消息的调用。后续 ACK 与日志分开处理。不能假定任意日志配置都会显示全部字段，不能把日志当认证成功 ACK。

| 输出字段 | 静态来源及边界 |
| --- | --- |
| Version／Platform1／Platform2 | 常量 `0`、`QCOM`、`SM8650`；Version 不是包版本 16.0.5.740 |
| Mode | `0x149a8ba8` 读取 `0x149da658`：非零选 `W`，零选 `R`。该字节文件初值为 1；`0x149a1e20–0x149a1e64` 解析 `EnableFlash` 后可更新。它与下文 AUTH_INTRANET／AUTH_INTERNET 是两组不同状态 |
| ID | `0x149aaf64` 从地址 `0x221c8610` 读 32 位值，日志自称 `oplus_get_soc_serial_number`；`getsigndata` 排除 0／0xffffffff，再用 `%x` 和 9 字节缓冲写到 `0x8025b281`。这是不强制左补零的十六进制文本，不直接等同 IMEI 或 Android ID |
| Rand | `0x149a0d3c` 请求运行时提供器返回 16 字节；随后只载入首个 64 位值，经 `0x149a7fd8` 逐半字节格式化成 **16 个小写十六进制字符**，在 `0x8025b28a` 保存并加终止符。消息复制的是这 16 个字符，不是 16 字节原始随机值；熵来源、更新频率及重用条件仍未证明 |
| ProjectWrite／ProjectRead | 两处均输出常量 `00000`，不是已核实的项目号 23631 |
| DigestWrite | `0x8025b29b` 的 64 字符字段。`0x149a0ca4` 对接收路径交付的表缓冲／长度计算 32 字节摘要，转成 64 字符并小写化。不能直接用整份 33,144 字节 MBN 的文件哈希代替；进入该函数的精确有效范围仍需与表接收／解析路径对齐 |
| DigestRead | `0x8025b2dc` 的 64 字符字段。安全状态路径通过 `0x149a895c` 定位、`0x149a44c0` 读取一份 512 字节对象，`0x149a0dac` 验证后复制其 +0x40 字段。关闭安全状态或读取／验证失败会复制固定 64 字符占位串；因此字段存在不证明存储对象读取成功 |
| NV | `0x149a10a0` 经存储定位／读取，检查 `OSIG` 前缀后对 0x160 字节调用 Base64 编码，输出缓冲为 `0x8025b41d`、容量 0x200。失败分支清零该缓冲。它不是包名中的 nv00000000 等标识，也没有被直接复制到下面的 208 字节消息 |
| SecureBoot | `0x149a4c9c` 查询结果决定日志。查询失败也可落到非零结果，不能仅凭这行还原全部 fuse 状态或判断可跳过认证 |

DigestRead 的占位文本完整保存在证据 JSON 的 `0x149ce688` 项；它不是本次取得的设备摘要。`getsigndata` 对部分辅助失败采用占位／空 NV 后继续，因此最终前序 ACK 也不能单独证明这些辅助材料有效。

## verify 的待验消息

`0x149a1224` 先将 208 字节清零，再按下表复制。字段名按日志及用途标识；所有字符均指 ASCII 字节。表中长度包括指令实际复制的终止符，未覆盖字节保持零。

| 消息偏移 | 复制长度 | 内容／来源 | 指令依据 |
| --- | ---: | --- | --- |
| 0x00 | 4 | `OSIG`，不含终止符 | `0x149a1c7c` |
| 0x04 | 2 | `0\0`，Version | `0x149a1270–0x149a127c` |
| 0x08 | 2 | 首次 `Y\0`；失败后改为 `N\0` | `0x149a1280–0x149a1290`、`0x149a137c–0x149a1388` |
| 0x0c | 1 | `W` 或 `R`；其余槽位仍为零 | `0x149a1294–0x149a12d8` |
| 0x10 | 5 | `QCOM\0` | `0x149a1d0c` |
| 0x18 | 7 | `SM8650\0` | `0x149a1d00` |
| 0x20 | 8 | ID 缓冲前 8 字节；不是解析后的整数 | `0x149a12f4–0x149a1304` |
| 0x30 | 16 | Rand 文本，不含终止符 | `0x149a1308–0x149a1314` |
| 0x40 | 64 | DigestWrite 文本，不含终止符 | `0x149a1318–0x149a1320` |
| 0x80 | 64 | DigestRead 文本，不含终止符 | `0x149a1324–0x149a132c` |
| 0xc0 | 6 | `00000\0`，ProjectWrite | `0x149a1330–0x149a1340` |
| 0xc8 | 6 | `00000\0`，ProjectRead | `0x149a1344–0x149a1350` |

零填充区为 0x06–07、0x0a–0b、0x0d–0f、0x15–17、0x1f、0x28–2f、0xc6–c7、0xce–cf。日志的分号、空格、字段名、NV 文本及 SecureBoot 行均不直接进入这个消息。不能对整段日志求摘要来替代该布局。

首次验签成功后设置状态 1，并记录 `AUTH_INTRANET`；失败后只把 +0x08 改成 `N\0`，重算并再次验签，成功设状态 2，记录 `AUTH_INTERNET`。这些名字是加载器状态名，不证明本次连接了内网或互联网签名服务。前次“模式 1／2”应理解为成功后的枚举值，不能把数值 1／2 填入消息 +0x08。

接收边界沿用前次证据：`verify` 先检查 getsigndata 前序状态，发出进入 raw 阶段的响应，再要求接收 4096 字节；前 256 字节交给验签路径。本轮没有恢复其余 3840 字节的完整契约，也没有发送、补零或构造可用响应。

## 公钥选择与验证算法

`0x149a1d18` 固定返回两个字符串地址：模数 `0x149ce818`、指数 `0x149cea19`。`0x149a4610 → 0x149a4740 → 0x149a46e0` 以基数 16 读入它们。模数是 512 个十六进制字符，即 2048 位；指数为十六进制 `10001`，即 65537。大端 256 字节模数的 SHA-256 为：

```text
56cceb8ef82b2428d534769c09898c689d5cd718c42922a416c9c77c85800331
```

完整公钥常量在证据 JSON 中。首次 Y 和回退 N 共用同一个公钥描述符；该分支没有按 NV、GKI、项目号、联网状态重新选钥。另一个 512 字节存储对象验证路径也调用同一常量助手。这不等于所有模块、Sahara 或 SVIP 表的信任根都相同，更不说明可凭公钥生成签名。

验证函数先对消息生成 32 字节摘要，再以算法 ID 9 调用 `0x149c5964 → 0x149c5720`。后者组装 `00 01 FF…00` 和 DER DigestInfo，再做 RSA 公钥运算、全块比较；算法表 `0x149d5500` 将 ID 9 对应到 OID `2.16.840.1.101.3.4.2.1`（SHA-256）。这是 RSA-2048／SHA-256／PKCS#1 v1.5 验证结构，不是 RSA-PSS。本轮只确认代码与常量，没有对任意候选签名做成功验签实验。

## 已有工具是否提供签名获取流程

继续检查已缓存的固定提交源码，提交号和来源沿用[前次报告](authentication-inputs.md)。范围为 OplusEdlTool 的 MainWindow／EdlService，Toolkit 的前端事件处理、lib.rs 分派、firehose_service、command_util，以及前次已查的 Linux fh_loader 文件发送路径；不是对所有第三方程序或未缓存依赖的穷尽审计。

- OplusEdlTool 手动进入和 StartFlash 都读取预选的 Digest／Sig 路径，未在这些调用链中发现 getsigndata 输出解析、208 字节消息构建、签名服务请求／响应或响应与当前会话绑定的检查。
- Toolkit 自动路径同样消费现成文件。[高级面板](https://github.com/snowwolf725/OPlus_EDL_Toolkit/blob/895678d4bb279703f3f4f0be775460489ea421d2/src/composables/useAdvancedPanelEventHandler.js)没有专门的 getsigndata 项，但允许编辑 XML；[run_command](https://github.com/snowwolf725/OPlus_EDL_Toolkit/blob/895678d4bb279703f3f4f0be775460489ea421d2/src-tauri/src/lib.rs#L300)可将内容交给通用 XML 执行器。这只能证明有手工命令通道，不能证明其实现了挑战解析、签名取得或完整握手。
- `--signeddigests` 路径只是传送已选文件。Loader 根证书摘要识别也不等于选择本报告中的会话验签公钥或获得对应签名。

因此，未查到可供当前加载器复用的端到端“取得挑战 → 取得合法签名 → 匹配当前会话 → 发送并确认”的实现。不从 AUTH_INTERNET 名称猜测服务器 URL、账户要求或是否收费。

## 补入验收计划的协议缺口

| 环节 | 已有证据 | 仍需补齐，当前不能通过的条件 |
| --- | --- | --- |
| 收集挑战 | 日志模板、来源、输出开关、前序状态 | 取得完整日志和 ACK 的规则；处理缺失、占位摘要、空 NV；确定运行时字段何时刷新 |
| 对齐待验消息 | 208 字节偏移、字符编码、零填充、Y/N 与 W/R 区分 | 用合法的同会话样本核对逐字节布局，特别是 ID 尾字节、表摘要范围及读取摘要的有效性 |
| 获得签名 | 固定公钥及验证算法已定位 | 合法签名材料或有依据的签发协议、响应格式、有效期、错误处理；公开公钥不能补齐此项 |
| 传输与结束 | 4096 字节接收、前 256 字节验签、前序和结果状态 | 尾部契约、日志／ACK／raw 边界、失败停止条件、会话重用行为；不能拿发送进程退出 0 替代验签结果 |
| 后续权限 | W/R 状态、AUTH 枚举、公钥关系已区分 | 与 sha256init、SVIP 表、VIP label 的完整权限链；configure 成功不证明此链完成 |

完整认证输入仍标记为未齐。前次 super 组装、短容器转换和 VIP label 的缺口继续保留。本轮产物用于离线审计与后续验收设计，不是可直接执行的设备认证方案。
